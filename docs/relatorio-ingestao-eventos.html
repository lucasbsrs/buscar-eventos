01 — O pedido

Objetivo e escopo

"Esse projeto tem como objetivo mapear os eventos otakus e geeks pelo Brasil (...) gostaria de alguma ideia de mapear de forma automatizada pelo máximo de eventos pelo Brasil. Também gostaria de pegar essas informações nos sites e colocar aqui na plataforma (...) e depois entrar nos links do site para fazer suas compras. Como isso poderia ser feito de forma automatizada sem muita intervenção humana?"
Visão do produto Plataforma onde o usuário descobre o evento geek/otaku mais próximo dele, no Brasil inteiro.
Pedido concreto Captar e extrair automaticamente dados de eventos em sites de terceiros e publicá-los no app.
Restrição Mínima intervenção humana contínua — o usuário compra o ingresso no site original, não aqui.
02 — Decisões tomadas

Três escolhas que moldam o desenho

Confirmadas com você antes de escrever o plano final.

Fonte inicial de eventos Sites de convenções conhecidas Lista curada (Anime Friends, CCXP etc.) — alta precisão e baixa manutenção para o MVP, em vez de agregadores de categoria.
Extração dos dados LLM + JSON-LD Tenta dados estruturados (schema.org) de graça primeiro; usa a API da Claude só quando não há — generaliza entre sites sem seletor por fonte.
Agendamento do pipeline GitHub Actions Sem o limite de timeout das functions da Vercel; roda scripts Node comuns com secrets integrados.
03 — Arquitetura

Do site de origem até a tabela eventos

1
seeds.json → discover.ts
Percorre a lista curada de sites de convenção e coleta URLs candidatas — uma por evento ou página de programação.
2
extract.ts
Procura JSON-LD (schema.org/Event) na página; sem isso, limpa o HTML e envia à Claude API pedindo os campos estruturados e um score de confiança. Valida tudo com zod antes de seguir.
3
write.ts
Dedup por fonte_url único + checagem fuzzy (nome + cidade + data). Grava via cliente admin (service role, ignora RLS). Confiança baixa vai para revisão em vez de publicar direto.
4
.github/workflows/ingest.yml
Dispara o pipeline em cron (diário/semanal) e sob demanda via workflow_dispatch, com os secrets da service role e da API da Claude.
04 — Plano por fases

Do schema ao pipeline completo

Cada fase depende da anterior estar validada — a ordem não é arbitrária.

0
Fase 0 — Schema e cliente admin Falta 1 passo

Fundação: novas colunas de rastreamento de origem, filtro de status nas queries públicas, e um cliente Supabase isolado com a service role key (a anon key não tem permissão de insert/DDL).

  • ✓ Migration supabase/migration_ingestion.sql escrita — colunas origem, fonte_nome, fonte_url, external_id, status, confianca, atualizado_em + índices de dedup.
  • ✓ Tipos atualizados em src/types/evento.ts.
  • ✓ Filtro status = 'publicado' em buscarEventos e buscarEventoPorId (src/lib/db/eventos.ts).
  • ✓ Cliente admin criado em scripts/ingest/lib/supabase-admin.ts.
  • ✓ SUPABASE_SERVICE_ROLE_KEY e ANTHROPIC_API_KEY documentadas em .env.local.example.
  • ○ Pendente: rodar a migration no SQL Editor do Supabase — sem isso a home já foi testada e retorna column eventos.status does not exist.
Motivo do bloqueio: só a anon key está disponível para os scripts atuais, e ela não tem permissão de DDL — a migration precisa ser executada manualmente com privilégio de owner.
1
Fase 1 — MVP, execução manual Planejada

Primeiro fluxo completo ponta a ponta, disparado à mão (npm run ingest), sem cron ainda — valida qualidade de extração e dedup contra dados reais antes de confiar sem supervisão.

  • · scripts/ingest/sources/seeds.json — lista de ~15 a 30 sites de convenção.
  • · scripts/ingest/discover.ts — coleta de URLs candidatas por site.
  • · scripts/ingest/extract.ts — JSON-LD → fallback Claude API → validação zod.
  • · scripts/ingest/write.ts — dedup + upsert via cliente admin.
  • · Novas dependências: cheerio, zod, @anthropic-ai/sdk.
2
Fase 2 — Automação agendada Planejada

O mesmo pipeline da Fase 1, agora sem intervenção humana no dia a dia.

  • · .github/workflows/ingest.yml — cron diário/semanal + workflow_dispatch manual.
  • · Secrets no repositório: SUPABASE_SERVICE_ROLE_KEY, ANTHROPIC_API_KEY.
  • · Log do run (novos, atualizados, em revisão, erros) — falha precisa ser visível, não silenciosa.
  • · Rate limiting por domínio, respeito a robots.txt, cache por hash de conteúdo (evita reprocessar e reconsultar a IA à toa).
3
Fase 3 — Ampliar fontes Planejada

Só depois de validar as fases 1 e 2 com dados reais.

  • · Incluir agregadores por categoria (Sympla, Ingresso.com, Disk Ingressos) como fonte de descoberta de eventos novos, não só a lista curada.
  • · Checar os termos de uso de cada site antes de incluir — maior volume, maior atenção necessária.
  • · Recalibrar o limiar de confiança com base na taxa real de falso positivo/negativo observada.
4
Fase 4 — Fila de revisão Opcional

Só vale a pena construir se a fila de pendente_revisao acumular volume relevante nas fases anteriores.

  • · Página /admin/revisao listando eventos pendentes, com aprovar/rejeitar.
  • · Precisa de controle de acesso — hoje o sistema de auth do app está removido, então depende de um stopgap (senha via env) ou de restaurar o auth antes.
05 — Schema novo

Colunas adicionadas em eventos

Todas aditivas e opcionais/padrão preenchido — nenhuma quebra o comportamento atual de cadastro manual.

ColunaTipoPara quê
origemtext, padrão 'manual'Distingue evento cadastrado por pessoa de evento capturado pelo scraper.
fonte_nometext, opcionalNome legível da fonte (ex. "sympla", "anime_friends_site").
fonte_urltext, opcional, únicoURL canônica da página de origem — chave de dedup principal.
external_idtext, opcionalID do evento na fonte original, quando disponível.
statustext, padrão 'publicado'publicado / pendente_revisao / rejeitado — controla o que aparece publicamente.
confiancanumeric(3,2), opcionalScore 0–1 da extração via LLM; abaixo do limiar vai para revisão.
atualizado_emtimestamptzMarca re-sincronizações do pipeline sobre o mesmo evento.
